# 原型需求

一份需求数据，同时生成可点击的原型和完整的需求文档，打包成一个离线 HTML。原型里每个可点元素都要属于已登记的功能点；需求缺说明时构建不通过；没有依据的内容标“AI 假设”或“待确认”。

## 交付物

- `<项目目录>/<产品名>-原型需求.html`，双击即可打开。首页是需求文档（全文，可导出 Markdown）；各端页面左侧是目录，中间是设备画板，右侧是本页需求，画板上的编号圆点与功能点卡片一一对应；另有核心流程演示，需求文档“核心流程”一章开头是按 `flows` 自动画的总流程图。顶部“切换”下拉框在三者之间切换。
- 原型阶段（流程 E）交付 `<项目目录>/<产品名>-原型.html`：打开直接进第一个端的首页，没有需求文档和需求面板，编号圆点默认隐藏。
- 托管原型引用了网络脚本或样式、该端写了 `online: true` 时，交付物标为“需联网”。

## 任务路由

| 用户意图 | 走哪条流程 |
| --- | --- |
| 有需求材料或只有几句话，要出原型/需求 | A. 新建 |
| 需求还没定，只想先让人看到产品样子，不写需求说明 | E. 原型阶段 |
| 已有一个 HTML 原型（可能还有一份对不上的 PRD），要补需求、做标注、拿去评审 | B. 已有 HTML 补需求（读 `references/host-mode.md`） |
| 已有本技能产出的项目，要按评审意见修改 | C. 修改 |
| 基于上一版做 V1.1、只看本版变化 | D. 版本迭代（读 `references/iteration.md`） |

无法判断时问用户一句，不要猜。

## 流程 A：新建

1. **读材料，整理已知事实。** 能从文件、截图、已有原型里查到的事实自己查，不问用户。
2. **轻量澄清。** 读 `references/clarify.md`。最多 2 轮、每轮不超过 6 题，每题带推荐答案，用户回“是”即采纳。材料已经足够时跳过提问。
3. **出范围清单，等用户确认。** 列出端、页面、每页的状态和功能点、出线框还是高保真、本期不做、AI 假设、待确认。**用户确认前不写任何页面代码。** 用户改了清单就按改动执行，只有你据此另加的内容才再问。
4. **建项目，写范围基线。** `node scripts/new.mjs <项目目录> --name "产品名" --id 英文短名 --end pc:端名称 [--end mobile:端名称] [--hifi]`。不加 `--hifi` 是线框，加了生成 `prd/theme.css` 骨架（托管模式不能用）。项目目录默认放在需求材料旁边，`--id` 给一个稳定的英文名。生成的端 ID：第一个 PC 端为 `pc`、第一个手机端为 `m`，同类再加为 `pc2`、`m2`。建好后、写页面前，按第 3 步确认的清单写 `prd/scope.json`，`prd/kit.js` 里的公共导航功能点也要列入（格式见 `references/spec-format.md` 文末）。
5. **写需求数据。** 读 `references/spec-format.md`，先写 `prd/product.js`（背景、范围、角色、端、全局规则、数据字典、流程、澄清记录）。
6. **逐页写页面。** 读 `references/components.md`。每个页面一个文件 `prd/pages/<编号>-<名称>.js`；脚手架生成的 `*-page.js` 是模板，改名后填写，页面 ID 不能重复。**先写 states 和 fns，再按 fns 写 render**，render 只画 fns 里登记的东西，用 `data-fn` 把元素挂到功能点上。
   - 表单的必填和长度校验、提交、搜索筛选用 `h.form`、`h.fld` 的 `req`/`min`/`max`、`h.submit`、`h.search`、`h.rows` 声明，行为由组件实现；不要在页面里另写校验，也不要用跳转按钮代替提交。`fields` 里的 `required` 要与 `h.fld` 的 `req` 一致。
   - 写法参考 `examples/course-mgmt/prd/`（列表搜索、新建弹窗的校验与提交、详情抽屉，高保真）和 `examples/leave-approval/prd/`（手机端 + PC 端、多状态、流程、数据场景，线框）。
   - 核心流程涉及的功能点建议写 `ac`（前置条件、用户操作、预期结果），没写只给 `AC_MISSING` 提醒。流程里的关键分支在那一步写 `branch`（如 `'未诊断'`），会标在总流程图的箭头上。
   - 出高保真时，先按 `references/hifi.md` 在 `prd/theme.css` 写下视觉方向和设计变量，把一条代表流程画完并截图看一眼，确认方向后再写其余页面。
   - 写作中新补的规则级假设直接标 `[AI 假设]`，不必停下来再问，汇报时列出。
7. **构建并修到通过。** `node scripts/build.mjs <项目目录>`，按输出修改，代码含义见 `references/audit-codes.md`。不要为了通过检查而删掉真实需求，也不要把真实功能塞进 `h.demo()`。`SCOPE_ADDED` / `SCOPE_REMOVED` 按硬性规则“范围确认”处理；提醒的是脚手架生成的公共导航（`公共/pc-shell/…`、`公共/m-shell/…`）时，说明基线漏写了，补进 `scope.json`，不要删导航。
8. **验证一条核心流程和一个失败分支，再检查截图。** 在交付 HTML 里实际操作，确认行为和需求一致（如必填为空时提交被拦、提交失败后可重试、成功后列表更新），结构检查通过不代表交互成立。截图用 `node scripts/snap.mjs <产物.html> --view "#/p/P02/reject"`：默认截需求文档和各端首页，`--view` 追加复杂页面或弹层状态（`#/p/<页面ID>/<状态ID>` 会应用该状态的演示数据）。修掉重叠、溢出、圆点压字（用功能点的 `dot` 调整位置）。
9. **汇报。** 见下方“交付汇报”。

## 流程 B：已有 HTML 补需求

读 `references/host-mode.md`。要点：

- 不修改用户的原文件；原型放在 sandbox iframe 中原样运行，本地 CSS/JS/图片构建时内联。
- 原型引用的网络脚本或样式会阻止交付（`HOST_NET`）。确需联网的端在 `ends` 里写 `online: true` 放行，交付物和汇报里标“需联网”。图片和字体只提醒。
- 先跑 `scripts/probe-host.mjs` 探测：全局函数、页面/弹层容器、可交互元素和建议选择器，以及 iframe 自检测、原生对话框、跳转顶层窗口等风险。
- 页面状态用 `enter` 到达、用 `match` 识别；功能点用 `sel` 绑定原有元素。
- 有 PRD 时以 PRD 为需求依据，原型是界面依据；两者冲突放进澄清问题。
- 原型有、需求不做（或不在本次评审范围）的元素写进 `end.ignore`；需求有、原型没画的功能点写 `gap`。两类差异在需求文档“需求与原型的差异”一章集中列出。

## 流程 C：修改

同一版本内按评审意见修改，不升版本、不写 `changes`。

1. 找到项目的 `prd/` 目录（交付 HTML 旁边）。只改 `prd/` 下的源文件，不手改交付 HTML。
2. 评审意见改到对应位置：页面/状态/功能点/字段/规则。意见是交付 HTML 里导出的 JSON 时，先运行 `node scripts/merge-comments.mjs <意见1.json> [意见2.json …] -o 评审意见合并.md --prd <项目目录>`，按合并稿的 `#序号` 逐条处理（见 `references/comments.md`）。新增的功能点同时在 render 里实现并绑定，删掉的同时从 render 里删掉。
3. 来源写评审结论，如 `src: '11/04 评审意见 1'`；来自导出的 JSON 时写 `src: '评审意见 #3（张三）'`。用户确认了某条“待确认”或“AI 假设”时，改写内容、去掉标记和 `status`，`src` 写确认来源。
4. 评审推翻了某条澄清结论时，在该条 `clarify` 的 `a` 后注明“（11/04 评审改为……）”，不删原记录。
5. 构建，增删按硬性规则“范围确认”处理（用户要求按本轮评审意见修改时，其中明确要求的增删算已确认），汇报改了哪些功能点。需要单独追溯评审修改时，可以在 `releases` 加一个小版本（如 V1.0.1）并按流程 D 记录。

## 流程 D：版本迭代

读 `references/iteration.md`。在 `releases` 追加新版本，变化写在对应条目的 `changes` 里；不重写旧内容。构建会把上一版交付文件自动归档到 `归档/`。本版范围清单确认后，增删按硬性规则“范围确认”处理。

## 流程 E：原型阶段

适用：需求还没定，只想先给领导或同事看产品样子。按流程 A 走，差异如下：

- 澄清最多 1 轮；范围清单只列页面、状态，以及功能点的编号和名称，不写依据和交互说明。
- 建项目后，在 `prd/product.js` 的 `W.product({` 后面加一行 `stage: 'prototype',`；范围基线照写。
- 状态写 `id` 和 `label`，功能点写 `id` 和 `name`，`data-fn` 绑定和完整模式一样。没有依据的字段、`when`、`errors` 留空，不写“待补充”“TODO”（`TEXT` 会报错）。可点元素仍要登记，登记了的功能点也要画出来。
- 构建不加 `--md`（会直接报错）。需求说明类的检查降为提醒，原型本身的错误照常阻止交付；命令行打印的待确认、AI 假设数量和 `AC_MISSING` 是正常输出。
- 托管模式也能用原型阶段，`sel` 绑定和 `ignore` 原因照常要写（`HOST_SEL`、`HOST`、`UNREGISTERED` 不放宽）。
- 汇报：交付路径、页面和功能点数量、顶部“原型阶段 · 结构检查通过”（写了 `online: true` 时带“需联网”），降为提醒的条数一句带过，列出最重要的待确认和 AI 假设。说明需求定了以后删掉 `stage` 那一行重新构建，降为提醒的项会变回错误，按流程 C 补齐；旧的 `-原型.html` 不会自动删除，提醒用户可以手动删。

## 硬性规则

- 原型只画范围清单里的功能。演示用的切换控件（如“以新用户登录”）放进 `h.demo()`，它们不进需求。
- 没有依据的规则、口径、字段校验，写成“… [AI 假设]”或标 `status: "assumed"`；需要业务方拍板的写“… [待确认]”或 `status: "pending"`。不得把推测写成已确认。每个功能点要么有 `src`（依据），要么是 `assumed` / `pending`。
- **范围确认。** 用户确认过的范围清单、明确的修改指令（如“加一个导出按钮”）都算已确认，不再重复问。构建后逐条核对 `SCOPE_ADDED` / `SCOPE_REMOVED`：都在已确认范围内的，直接 `--scope-baseline --confirmed-at <确认日期>` 刷新基线；超出的，误加的删掉，想保留的在汇报里列给用户，确认后再刷新（确认前它们留在需求文档“范围确认后新增”一章）。只改文字不用刷新。新项目必须写 `scope.json`，没有它的旧项目照常构建，只是不做增删对比。
- 检查未通过不交付。`--draft` 只用于排查画面，产物不可交给用户。
- 页面代码不写色值，内联样式只用于尺寸、字号和字距。线框用 `h.*` 组件和 `wire.css` 工具类；高保真的视觉写在项目的 `prd/theme.css`（可选 `prd/theme-kit.js`），按 `references/hifi.md` 设计，不套用任何公司规范。
- 托管模式下不修改用户的原 HTML 文件。
- 原型阶段（`stage: 'prototype'`）不是绕过检查的开关，完整需求项目不要写这一行。

## 交付汇报

用几行说清楚：

- 交付文件路径（和 Markdown 路径，如果导出了）。
- 规模：端、页面、状态、功能点数量；结构检查通过，交互元素归属率（托管模式另报 ignore 的元素数和 gap 数）。
- **待确认**和 **AI 假设**各几条，列出最重要的 3–5 条请用户确认；澄清中采纳推荐、未经用户明确确认的结论也列出。
- 高保真时：说明实际的视觉依据（用户给的设计稿、截图、品牌色），没有依据的部分说明由 AI 自拟；列出主色和字阶，请用户确认方向。
- 标为“需联网”时，说明交付后需联网，并列出对应的网络脚本或样式地址。
- 原型阶段按流程 E 的最后一条汇报。

## 命令与参考文件

路径相对本技能目录；需要 Node 18+ 和本机 Chrome / Edge / Chromium（找不到时设置 `CHROME_PATH`）。

```bash
node scripts/new.mjs <项目目录> --name "产品名" [--id 英文短名] --end pc:管理后台 [--end mobile:员工手机端] [--hifi | --host <已有原型.html>]
node scripts/probe-host.mjs <已有原型.html> [--steps '[{"js":"showPage(\"x\")"}]'] [--boot '[...]'] [--shot a.png]
node scripts/build.mjs <项目目录> [--md] [--csv] [--export-pack] [--out 文件名.html] [--draft]
node scripts/build.mjs <项目目录> --scope-baseline [--confirmed-at 2026-11-04]   # 增删都已确认后刷新 prd/scope.json
node scripts/snap.mjs <产物.html> [--view "#/p/P01/list"]... [--only] [--out 截图目录]
node scripts/merge-comments.mjs <意见1.json> [意见2.json ...] [-o 评审意见合并.md] [--prd <项目目录>]
node scripts/test-skill.mjs                                                        # 技能自身回归测试
```

只在进入对应步骤时读对应文件：

| 什么时候读 | 文件 |
| --- | --- |
| 澄清、写范围清单 | `references/clarify.md` |
| 写 `product.js`、页面数据、`scope.json` | `references/spec-format.md` |
| 写 render：组件、交互属性、页面写法 | `references/components.md` |
| 出高保真，或已有项目自带 `theme.css` / `theme-kit.js` | `references/hifi.md` |
| 已有 HTML 补需求（流程 B） | `references/host-mode.md` |
| 版本迭代、本版变化（流程 D） | `references/iteration.md` |
| 处理导出的评审意见（流程 C） | `references/comments.md` |
| 导出 CSV、研发包（`--csv`、`--export-pack`） | `references/export-csv.md` |
| 按角色过滤（`fn.roles`） | `references/roles.md` |
| 构建报错或提醒的代码 | `references/audit-codes.md` |

`assets/` 下是运行时、新项目模板和第三方库（Marked、DOMPurify、Mermaid 及许可），一般不用读。
