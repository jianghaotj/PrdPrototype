# 原型需求

一份需求数据，同时生成可点击的线框原型和完整的需求文档，打包成一个离线 HTML。

## 为什么这样设计

| 常见问题 | 本技能的做法 |
| --- | --- |
| 原型多出需求里没有的功能 | 原型里每个按钮、链接、输入框都必须属于一个已登记的功能点，否则构建失败 |
| 照着原型写的需求缺斤短两 | 构建时逐页逐状态渲染原型反查需求：状态要有出现条件，功能点要有交互说明，有输入就要有字段定义，有列表就要有空数据说明，有提交就要有异常处理 |
| 需求不清，AI 自由发挥 | 先轻量澄清、再确认范围清单，确认后才画；没有依据的内容必须标“AI 假设”或“待确认”，在原型和文档里都看得见 |
| 原型和文档两份文件，读着不连贯 | 只交一个 HTML：左侧页面目录，中间原型，右侧本页需求；顶部“切换”下拉框选需求文档（全文，可导出 Markdown 和打印 PDF）、各端原型或核心流程 |

## 交付物

`<项目目录>/<产品名>-原型需求.html`，双击即可打开。托管原型引用了网络脚本或样式并写了 `online: true` 时，交付物标为“需联网”，见下文“交付汇报”。

原型阶段（`product.js` 写 `stage: 'prototype'`，见流程 E）交付的是 `<项目目录>/<产品名>-原型.html`。打开直接进第一个端的首页，没有需求文档栏目和需求面板，编号圆点默认隐藏。

- **需求文档**（首页）：概述、范围、角色、信息架构、核心流程、全局规则、逐页需求、公共组件、数据字典、验收条件（有 `ac` 时）、需求与原型的差异（托管模式）、范围确认后新增（有范围基线时）、待确认与 AI 假设、澄清记录、变更记录；右侧是评审摘要和构建检查结果。
- **各端页面**：左侧目录，中间设备画板（PC 浏览器框或手机框），右侧需求面板（页面目标、状态与出现条件、编号功能点卡片、页面规则、入口、跳转）。画板上的编号圆点与卡片一一对应。
- **核心流程**：逐步演示，可直接点画板前进。
- 顶部“切换”下拉框：在需求文档、各端原型、核心流程之间切换，选项下写着端类型和页面数。窗口宽 1100 及以下时顶栏分两行，下拉框在第一行。键盘可用：↓ 打开，↑ ↓ Home End 移动，Enter 选中，Esc 收起。原型阶段没有“需求文档”这一项。
- 工具：热区 `H`、标注圆点 `N`、缩放、目录/需求面板开关、重置演示数据、本版变化（多版本时）、意见（顶栏“意见”，评审意见可导出 JSON，见 `references/comments.md`）、清单（原型阶段顶栏导出研发测试 CSV，见 `references/export-csv.md`）、角色下拉（有 `product.roles` 时按角色过滤，见 `references/roles.md`）。

## 任务路由

| 用户意图 | 走哪条流程 |
| --- | --- |
| 有需求材料或只有几句话，要出原型/需求 | A. 新建 |
| 需求还没定，只想先让人看到产品样子，不写需求说明 | E. 原型阶段 |
| 已有一个 HTML 原型（可能还有一份对不上的 PRD），要补需求、做标注、拿去评审 | B. 已有 HTML 补需求（读 `references/host-mode.md`） |
| 已有本技能产出的项目，要按评审意见修改 | C. 修改 |
| 基于上一版做 V1.1、只看本版变化 | D. 版本迭代（读 `references/iteration.md`） |

无法判断时问用户一句，不要猜。

## 流程 A：新建

1. **读材料，整理已知事实。** 能从文件、截图、已有原型里查到的事实自己查，不问用户。
2. **轻量澄清。** 读 `references/clarify.md`。最多 2 轮、每轮不超过 6 题，每题带推荐答案，用户回“是”即采纳。材料已经足够时跳过提问。
3. **出范围清单，等用户确认。** 列出端、页面、每页的状态和功能点、出线框还是高保真、本期不做、AI 假设、待确认。**用户确认前不写任何页面代码。** 用户改了清单，只就改动部分再确认一次。用户确认后，进入第 4 步建项目；基线在第 4 步之后写（见第 4 步末尾）。
4. **建项目。** `node scripts/new.mjs <项目目录> --name "产品名" --id 英文短名 --end pc:端名称 [--end mobile:端名称] [--hifi]`。不加 `--hifi` 是线框；加了生成 `prd/theme.css` 骨架，PC 端默认 1440×900，视觉由你按 `references/hifi.md` 设计。`--hifi` 不适用于托管模式。项目目录默认放在需求材料旁边。`--id` 用于浏览器保存演示数据，建议给一个稳定的英文名。生成的端 ID：第一个 PC 端为 `pc`、第一个手机端为 `m`（同类再加为 `pc2`、`m2`），页面的 `end` 引用它。
   **建项目后、写页面前，写范围基线 `prd/scope.json`**（格式见 `references/spec-format.md`）：页面、状态、功能点照第 3 步确认的清单写，并把 `prd/kit.js` 里的公共功能点一并列入，即 `公共/pc-shell/pc-nav` 和 `公共/m-shell/m-tab`（端 ID 不同时按实际生成的 ID）。漏掉这两条，第一次构建会误报 `SCOPE_ADDED`。
5. **写需求数据。** 读 `references/spec-format.md`，先写 `prd/product.js`（背景、范围、角色、端、全局规则、数据字典、流程、澄清记录）。
6. **逐页写页面。** 读 `references/components.md`。每个页面一个文件 `prd/pages/<编号>-<名称>.js`；脚手架生成的 `*-page.js` 是模板，改名后填写，页面 ID 不能重复。**先写 states 和 fns，再按 fns 写 render**。render 只画 fns 里登记的东西，用 `data-fn` 把元素挂到功能点上。参考 `examples/leave-approval/prd/` 的写法（高保真样例见 `examples/course-mgmt/prd/`，读 `references/hifi.md`）。表单的必填和长度校验、提交、搜索筛选用 `h.form`、`h.fld` 的 `req`/`min`/`max` 选项、`h.submit`、`h.search` 和 `h.rows` 声明，行为由组件实现，不要在页面里另写校验（见 `references/components.md`）。`fields` 里的 `required` 要与 `h.fld` 的 `req` 一致。核心流程涉及的功能点建议写 `ac`（前置条件、用户操作、预期结果），没写只给 `AC_MISSING` 提醒。出高保真时，先在 `prd/theme.css` 写下视觉方向和设计变量，把一条代表流程（如列表、新建、提交、列表更新）画完并截图看一眼，确认方向后再写其余页面。写作中新补的规则级假设直接标 `[AI 假设]`，不必停下来再问，汇报时列出。
7. **构建并修到通过。** `node scripts/build.mjs <项目目录>`。未通过时按输出修改，代码含义见 `references/audit-codes.md`。不要为了通过检查而删掉真实需求，也不要把真实功能塞进 `h.demo()`。范围基线已在第 4 步之后写好，这一步不需要 `--scope-baseline`。写页面时多出来的页面、状态或功能点会被提醒为 `SCOPE_ADDED`。这些是清单之外的内容：误加的删掉，确认保留的列给用户。若提醒的是脚手架生成的公共导航（`公共/pc-shell/…`、`公共/m-shell/…`），说明基线漏写了，应补进 `scope.json`，不要删掉导航。
8. **看一眼画面。** `node scripts/snap.mjs <产物.html> --view "#/p/P02/reject"`：默认截需求文档和各端首页，`--view` 追加复杂页面或弹层状态（地址 `#/p/<页面ID>/<状态ID>` 打开时会应用该状态的演示数据）。查看截图，修掉重叠、溢出、圆点压字（用功能点的 `dot` 调整位置）。
9. **汇报。** 见下方“交付汇报”。

## 流程 B：已有 HTML 补需求

读 `references/host-mode.md`。要点：

- 不修改用户的原文件；原型放在 sandbox iframe 中原样运行，本地 CSS/JS/图片构建时内联。
- 原型引用的网络脚本或样式会阻止交付（`HOST_NET`），断网时原型会失效。确需联网的端在 `ends` 里写 `online: true` 放行，交付物和汇报里标“需联网”。图片和字体只提醒。
- 先跑 `scripts/probe-host.mjs` 探测：全局函数、页面/弹层容器、可交互元素和建议选择器，以及 iframe 自检测、原生对话框、跳转顶层窗口等风险。
- 页面状态用 `enter` 到达、用 `match` 识别；功能点用 `sel` 绑定原有元素。
- 有 PRD 时以 PRD 为需求依据，原型是界面依据；两者冲突放进澄清问题。
- 原型有、需求不做（或不在本次评审范围）的元素写进 `end.ignore`，原型上会被虚线框出；需求有、原型没画的功能点写 `gap`。两类差异在需求文档“需求与原型的差异”一章集中列出。

## 流程 C：修改

同一版本内按评审意见修改，不升版本、不写 `changes`。

1. 找到项目的 `prd/` 目录（交付 HTML 旁边）。只改 `prd/` 下的源文件，不手改交付 HTML。
2. 评审意见改到对应位置：页面/状态/功能点/字段/规则。意见是交付 HTML 里导出的 JSON 时，先运行 `node scripts/merge-comments.mjs <意见1.json> [意见2.json …] -o 评审意见合并.md --prd <项目目录>`，按合并稿的 `#序号` 逐条处理（格式见 `references/comments.md`）。新增的功能点同时在 render 里实现并绑定；删掉的功能点同时从 render 里删掉。
3. 来源写评审结论，如 `src: '11/04 评审意见 1'`；意见来自导出的 JSON 时，写 `src: '评审意见 #3（张三）'`，序号和作者取自合并稿。用户确认了某条“待确认”或“AI 假设”时，改写内容、去掉标记和 `status`，`src` 写确认来源。
4. 评审推翻了某条澄清结论时，在该条 `clarify` 的 `a` 后注明“（11/04 评审改为……）”，不删原记录。
5. 改完后先构建（不加 `--scope-baseline`），看 `SCOPE_ADDED` / `SCOPE_REMOVED`。有增删时，把这些条目逐条列给用户，说明是评审新增的还是误加的。**用户确认保留的条目后**，再执行 `--scope-baseline` 刷新基线，并加 `--confirmed-at <今天日期>`。误加的功能点直接删掉再构建。用户还没确认前不刷新，新增内容会继续以 `SCOPE_ADDED` 提醒，并留在需求文档“范围确认后新增”一章。只改文字、不增删时不需要刷新。
6. 重新构建，汇报改了哪些功能点。需要单独追溯评审修改时，可以在 `releases` 加一个小版本（如 V1.0.1）并按流程 D 记录。

## 流程 D：版本迭代

读 `references/iteration.md`。在 `releases` 追加新版本，变化写在对应条目的 `changes` 里；不重写旧内容。构建会把上一版交付文件自动归档到 `归档/`。本版范围清单确认后，先构建列出 `SCOPE_ADDED` / `SCOPE_REMOVED`，用户确认这些条目后，再用 `--scope-baseline` 刷新基线（做法同流程 C 第 5 步）。刷新后，本版确认的新增内容不再以“范围确认后新增”单列。

## 流程 E：原型阶段

适用：需求还没定，只想先给领导或同事看产品样子。这个阶段只做界面，需求说明留到需求定了再写。

1. **读材料。** 同流程 A 第 1 步。
2. **澄清最多 1 轮。** 读 `references/clarify.md`。材料已经够画页面时跳过提问。
3. **出范围清单，等用户确认。** 只列页面、状态，以及功能点的编号和名称，不写依据和交互说明。用户确认前不写页面代码。
4. **建项目和范围基线。** 用 `new.mjs` 建项目，同流程 A 第 4 步。在 `prd/product.js` 的 `W.product({` 后面加一行 `stage: 'prototype',`。然后按清单写 `prd/scope.json`，要求同流程 A 第 4 步。
5. **写页面。** 每个状态写 `id` 和 `label`，每个功能点写 `id` 和 `name`。`render` 里用 `data-fn` 把元素挂到功能点上，和完整模式一样。没有依据的字段、`when`、`errors` 留空，不写“待补充”。原型里的可点元素仍要登记；登记了的功能点也要画出来，否则报错。
6. **构建。** `node scripts/build.mjs <项目目录>`，不加 `--md`。需求说明类的检查降为提醒，原型本身的错误照常报错，按输出修到通过。命令行仍会打印待确认、AI 假设的数量和 `AC_MISSING` 提醒，这些是正常输出。
7. **看一眼画面。** 同流程 A 第 8 步。
8. **汇报。** 交付路径、页面和功能点数量、顶部“原型阶段 · 检查通过”。降为提醒的条数一句带过。列出最重要的待确认和 AI 假设。说明需求定了以后，删掉 `stage` 那一行重新构建。之前降为提醒的项会变回错误，错误清单就是还要补的需求，之后按流程 C 修改。旧的 `-原型.html` 不会自动删除，提醒用户可以手动删。

## 硬性规则

- 原型只画范围清单里的功能。演示用的切换控件（如“以新用户登录”）放进 `h.demo()`，它们不进需求、在热区里显示为虚线。
- 没有依据的规则、口径、字段校验，写成“… [AI 假设]”或标 `status: "assumed"`；需要业务方拍板的写“… [待确认]”或 `status: "pending"`。不得把推测写成已确认。
- 每个功能点要么有 `src`（依据），要么是 `assumed` / `pending`。
- 检查未通过不交付。`--draft` 只用于排查画面，产物不可交给用户。
- 视觉分两种。线框：优先用 `h.*` 组件和 `wire.css` 的工具类，不写颜色。高保真：配色、字阶、间距、圆角、组件状态由你按 `references/hifi.md` 设计，写在项目的 `prd/theme.css`（和可选的 `prd/theme-kit.js`）里，不套用任何公司规范，汇报时说明视觉是 AI 自拟的。两种情况页面代码都不写色值，内联样式只用于尺寸、字号和字距。
- 已有项目 `prd/` 下自带的 `theme.css`、`theme-kit.js`（包括从旧版规范包复制来的）是项目文件，构建照常纳入，不要为此改动或删除；用户要求换视觉时再按 `references/hifi.md` 改写。
- 托管模式下不修改用户的原 HTML 文件。
- 原型阶段（`stage: 'prototype'`）不是绕过检查的开关。完整需求项目不要写这一行。原型阶段只放宽需求说明类的提醒，原型本身的错误照样阻止交付。
- 原型阶段不写的内容留空，不写“待补充”“TODO”（`TEXT` 会报错）。
- 原型阶段也能用于托管模式（已有 HTML 补需求）。托管端仍要写 `sel` 绑定和 `ignore` 原因（`HOST_SEL`、`HOST`、`UNREGISTERED` 不放宽）；虚线框和圆点一起默认隐藏，按 `N` 显示，不记住；该端写 `online: true` 时，顶部标为“原型阶段 · 检查通过 · 需联网”。`--md` 不能用于原型阶段，会直接报错，不生成文件。

## 交付汇报

用几行说清楚：

- 交付文件路径（和 Markdown 路径，如果导出了）。
- 高保真时：说明视觉方案由 AI 自拟、没有对齐公司设计规范，列出主色和字阶，请用户确认方向。
- 规模：端、页面、状态、功能点数量；构建检查通过，交互元素归属率（托管模式另报 ignore 的元素数和 gap 数）。
- **待确认**和 **AI 假设**各几条，列出最重要的 3–5 条，请用户确认。
- 有范围基线时，列出“范围确认后新增”的条数和名称；没有确认的新增，请用户决定是否纳入本期。
- 构建检查标为“需联网”（有端写了 `online: true`）时，说明交付后需联网，并列出对应的网络脚本或样式地址。
- 澄清中采纳推荐、未经用户明确确认的结论。
- 原型阶段：交付路径，功能点数量，顶部“原型阶段 · 检查通过”。降为提醒的条数一句带过，并说明需求定了以后删掉 `stage` 重新构建即可。

## 命令速查

所有路径相对本技能目录；需要 Node 18+ 和本机 Chrome / Edge / Chromium（找不到时设置 `CHROME_PATH`）。

```bash
node scripts/new.mjs <项目目录> --name "产品名" --end pc:管理后台 --end mobile:员工手机端
node scripts/new.mjs <项目目录> --name "产品名" --end pc:管理后台 --hifi          # 高保真：生成 prd/theme.css 骨架，视觉自拟
node scripts/new.mjs <项目目录> --name "产品名" --host <已有原型.html>        # 托管模式
node scripts/probe-host.mjs <已有原型.html> [--steps '[{"js":"showPage(\"x\")"}]'] [--boot '[...]'] [--shot a.png]
```

## 资源导航

- `references/clarify.md`：轻量澄清的提问规则、格式和范围清单模板。
- `references/spec-format.md`：需求数据格式（产品、端、页面、状态、功能点、字段、规则、流程、演示数据）和写作要求。
- `references/components.md`：线框组件 `h.*`、交互属性、页面写法范式、样式覆盖的方法。
- `references/hifi.md`：高保真的做法：定视觉方向、设计变量、组件状态、真实感数据、自查。
- `references/host-mode.md`：为已有 HTML 补需求。
- `references/iteration.md`：版本迭代与本版变化。
- `references/comments.md`：评审意见的留存、导出 JSON 格式与合并（流程 C）。
- `references/export-csv.md`：功能点/字段/验收条件 CSV 与研发包（`--csv`、`--export-pack`）。
- `references/roles.md`：按角色过滤原型（`fn.roles` 与顶栏角色下拉）。
- `references/audit-codes.md`：构建检查代码与修改办法。
- `examples/leave-approval/`：线框基线样例（手机端 + PC 端、表单、列表、抽屉、弹窗、流程、数据场景）。
- `examples/course-mgmt/`：PC 高保真样例（视觉由 AI 自拟；列表搜索与分页、新建弹窗的校验与提交重试、详情抽屉）。
- `assets/runtime/`：浏览器外壳、组件、文档生成和检查逻辑；`assets/template/`：新项目模板（含 `--hifi` 用的 `theme.css` 骨架）；`assets/vendor/`：Marked、DOMPurify、Mermaid 及许可。

只在进入对应步骤时读取对应参考文件。
